ADAPT SPEC, REVISED

This is the working revision of spec/original.txt. Open questions are tasks in the spec project: python .claude/skills/rules-system/scripts/rules.py tasks --in spec. A note such as "(open: t13)" marks a point that task still has to settle.


Ethos:
	When using skills think of skills as an ongoing effort. skills are not set in stone and are maleable and ever changing. I want to improve skill use and capability as time goes on and as they are used.

"Adapt" skill is going to be a claude skill that is a meta level skill, a skill for skills.

 It will be the place where skills are born and skills are improved. The idea here is that this skill will be used by all agents to request new skills and to improve existing ones. As requests accrue, at some critical point, typically initiated by myself the human user (for now - but perhaps not in the future) the "Adapt" will execute a 'round', which is like a total sweep of processing from top to bottom where it performs actions based on its current state.


Where Adapt lives (configuration B, the current best contender):
	Adapt comes in two parts. The goal of a self-contained skill folder is dropped.
	- The shim: a thin skill inside the host project, at <host>/.claude/skills/adapt/. It holds only SKILL.md and the scripts a host instance runs: init, submit a request, read the manager's records, start a round (open: t22). It has no .claude tree of its own.
	- The workspace: everything else, in a folder outside the host repository, created at first init. Examples are ~/.adapt/<host name>/ or a folder beside the host; the exact place is open (t21). It holds Adapt's own .claude tree, its rules, and the capitalized root folders below.
	The other skills in the host's .claude/skills/ are Adapt's sibling skills. They serve the host project, and they are the skills Adapt repairs, extends and adds to.
	Adapt comes bundled with its own copies of two skills from this repo: rules-system and vector-search. It also carries a third skill of its own, META TOOLS. The handoff skill may join later; for now Adapt ships with these three. All three live in the workspace.
	Why B: every fence rests on documented Claude Code behavior.
	- The manager starts in the workspace. The host is not above it, so the skill and agent search, which walks up from the start folder, never reaches the host's skills or agents.
	- The manager reaches host files through the permissions.additionalDirectories setting. That setting grants file access and never loads the folder's skills, CLAUDE.md or rules. The --add-dir flag does load skills, so Adapt does not use it. The setting takes effect only once the workspace is trusted.
	- Adapt's inner skills are not under the host tree, so a host session can never discover them. They serve only the instances that inhabit Adapt.
	Set aside:
	- A: everything inside the skill folder, made its own git repository. It rests on untested behavior: discovery stopping at a git root, and lazy nested skill discovery.
	- D: a --bare manager. It needs an API key billed directly instead of the subscription login.
	- C, packaging the workspace's skills, agents and hooks as a plugin loaded with --plugin-dir, can still be added on top of B (open: t13).


How a session learns of Adapt:
	There is no CLAUDE.md file. Everything is scoped through rules. A gated rule in rules/INDEX.md tells a session about the Adapt skill when the session touches Adapt's files and folders, or when the user runs the Adapt init command. The rule is injected only when its gate matches, so a session that never touches Adapt pays nothing for it. The gate cannot match paths under .claude/skills/, so it matches the commands the shim runs, and the workspace.


The workspace's .claude tree:
	The workspace contains its own .claude tree, because Adapt is mainly run by a headless session started inside it. That session treats the workspace as its project.
	- .claude/settings.json: ordinary Claude Code settings. Its claudeMdExcludes setting lists glob patterns, matched against absolute paths, that stop every CLAUDE.md and CLAUDE.local.md above the workspace from loading. A managed-policy CLAUDE.md cannot be excluded. Its permissions.additionalDirectories names the host folders the manager may edit. The same file holds the hooks and permissions that keep each agent in its silo. It also sets promptCacheTtl and subagentPromptCacheTtl to 1h, because a subagent's requests otherwise keep only a five-minute cache even on a subscription, and because the main conversation drops to five minutes once the plan's included usage runs out. Cache warmth is a setting, not something to poll for: see spec/launch-options.md.
	- .claude/agents/: the two specialist definitions.
	- .claude/skills/: rules-system, vector-search and meta-tools.
	- .claude/hooks/: the scripts the settings call.
	There is no unscoped rule and no CLAUDE.md anywhere in this tree. graphify's installer writes two; Adapt's install script mines and deletes them at once (see Code intelligence for specialists). Adapt's rules live in the workspace's rules/ folder, gated by its own rules/INDEX.md.
	The workspace is the root of its own git repository and never sits inside another one, so the documented walk up to the repository root ends at the workspace itself.
	What the Claude Code docs and issue reports say (checked 2026-09-15):
	- Skills and agent definitions are found by walking up from the start folder to the repository root. No setting stops that walk.
	- Project settings are not inherited from parent folders.
	- claudeMdExcludes stops CLAUDE.md and rules files. --setting-sources affects settings files only, not skills, agents, CLAUDE.md, rules or hooks.
	- Permission deny rules gate Claude's own tool calls, not Claude Code's startup discovery, so a Read deny cannot stop a skill from loading.
	- The --bare flag skips hooks, skills, subagents, plugins, MCP servers, auto memory and CLAUDE.md, and never reads the subscription login, so it needs ANTHROPIC_API_KEY or an apiKeyHelper.
	What a probe proved (2026-09-15, a throwaway workspace outside this repo, since deleted):
	- A session started in a workspace outside the host loads none of the host's skills or agents. It listed only its own workspace skill and agent, plus Claude Code's bundled skills and built-in agents. This is B's main fence, confirmed.
	- The user's personal ~/.claude skills and agents DO load. They must be excluded.
	- skillOverrides "off" in the workspace settings removes a personal skill from the session. A permissions.deny entry of Agent(<name>) removes a personal agent. Both work by name, so the launcher regenerates them from what ~/.claude/skills and ~/.claude/agents hold at that moment.
	- CLAUDE_CONFIG_DIR gives the manager a config folder with no personal skills or agents at all, but that folder carries no credentials: the run ends with "Not logged in - Please run /login". It costs one login for that folder.
	- permissions.additionalDirectories is IGNORED until the workspace is trusted: "this workspace has not been trusted". The user accepts the trust dialog once in the workspace, or init writes hasTrustDialogAccepted for that path. This belongs in the install steps (t21).
	Chosen (2026-09-15): the regenerated exclusions, not a config folder of Adapt's own. See Stripping the manager.


Stripping the manager:
	The manager starts with as little as possible. A capability comes back only when a need for it shows up, one at a time, and each one that comes back is recorded with what needed it.
	- Personal skills and agents: the launcher regenerates the exclusions at every launch. It scans the user's skills and agents folders, writes a skillOverrides "off" entry for every skill name it finds and a permissions.deny entry of Agent(<name>) for every agent name, then starts the manager. It keeps a manifest of the names it has already nullified, so a name it has not seen before is nullified AND logged, and nothing new slips in unnoticed.
	- Personal settings and hooks: the user's settings file also carries their model choice, status line and hooks, and those hooks would run in the manager. --setting-sources project,local drops that file while leaving the login alone, because credentials are stored outside it. Untested (t13).
	- Bundled skills, such as code-review and loop, always load. The docs name disableBundledSkills to drop them. Untested (t27).
	- Built-in agents: CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS=1 removes Explore, Plan and general-purpose in a -p session. Every Agent call must then name one of Adapt's own specialists.
	- Plugins enabled in the user's settings still load their skills, commands and agents. Whether the workspace can switch one off is untested (t27).
	- Auto memory: off in the workspace settings, so nothing the manager or a specialist learns is written outside Adapt's own records.
	- MCP servers: none. The workspace ships no .mcp.json, and no MCP server is inherited, because MCP configuration is not read from parent folders.
	The aim is one set of moving parts, Adapt's own. Every variable that comes from outside the workspace is one more thing that can change under the manager without anyone changing Adapt.


Launching the manager:
	The launcher is a script in the shim. It regenerates the exclusions, then starts one session in the workspace.
	Five candidates were compared across authentication, lifetime, startup context, subagents, messaging, permissions, working directory, observability, failure, concurrency, effort and swappability: claude -p per round, -p with stream-json input, -p with --resume, claude --bg, and the Agent SDK. The comparison, the evidence and what is still untested are in spec/launch-options.md. It is the owner of that analysis; this section keeps only the decision.
	Chosen default: one claude -p run per round, no --resume and no carried conversation. The manager's context comes from files, its rules and vector-search, never from a long-lived transcript. A later round starts clean and reads what the last one wrote (open: t13).
	Ruled out for now: --resume, because a resumed run does not restore the --settings that carry the exclusions, and because the conversation would grow into the context store the spec rejects; the Agent SDK, because its documentation directs agents built on it to API-key authentication rather than the subscription login.
	Kept in view: claude --bg, the only candidate that survives between rounds, can be attached to and messaged, and restarts itself after a crash. Before adopting it, test that a background session moves itself into a worktree under .claude/worktrees/ before editing files, which would move the manager out of the workspace it was started in.
	A -p session binds a messaging inbox, so the host can message a running manager; it cannot show an approval dialog, so the launcher passes crossSessionInbound accept for held messages to be delivered (untested).
	Agent teams are never an option here: they need an interactive session and do not spawn in -p.
	Keeping startup context small, for the manager and for every specialist:
	- No CLAUDE.md, no unscoped rules, no bundled skills, no personal skills or agents, no MCP servers, no auto memory.
	- Rules arrive only when a gate matches what the agent touches.
	- A specialist is preloaded with the few skills it needs, and its definition sets omitClaudeMd, a short body, and a tools list that leaves out what it must not use. Every tool listed costs context.
	- Everything else is looked up on demand: the agent's own folders, its rules folder, and vector-search over the corpus as it grows.


Code intelligence for specialists:
	A specialist works on someone else's code, so it needs to see what calls what instead of reading whole files.
	- Claude Code's LSP plugins connect a language server, which gives definitions, references and type errors directly. The official marketplace has plugins for TypeScript, Python, Go, Rust and other common languages, and any plugin can carry its own .lsp.json for a language that has none. The language server binary must be on the machine.
	- A specialist should be able to add the one for its skill's language on its own. Plugins load at session start, so an installed or enabled plugin reaches the next session, not the running one. How a subagent does this without the interactive plugin command is open (t28).
	- A tool that builds a graph of the codebase, so an instance can see which parts affect which, is wanted on top of this. The user found one: graphify (github.com/Graphify-Labs/graphify, PyPI package graphifyy, double y, dual Apache 2.0 and MIT). Trialled on 2026-09-16 in a throwaway environment, since deleted (open: t29).
	What graphify is:
	- It parses code locally with tree-sitter, 37 languages, with no model and no API key, into graph.json: nodes, edges tagged EXTRACTED or INFERRED, and communities. The trial built 500 nodes, 1,153 edges and 18 communities from the rules-system scripts in seconds with `graphify extract <path> --code-only`.
	- Its CLI answers the questions a specialist asks: `query "<question>"` with a token budget, `path "A" "B"`, `explain "X"`, `affected "X"` for what a change reaches, `god-nodes` for the hubs, and `update <path>` to re-extract changed code without a model.
	- Docs, papers and images, and naming the communities, need a model: an API key for a backend, or the Claude Code session itself when the skill runs inside one. `--code-only` and `--no-label` keep it model-free.
	- It writes graphify-out/ next to whatever it scanned unless told otherwise with --out, and a global graph under ~/.graphify only when asked with --global. Its query log is off unless enabled.
	How Adapt installs it, differently from the README:
	- The package goes into a Python environment of the workspace's own, pinned to a version, rather than a user-wide tool. Python 3.12 is present; uv is not installed yet, and is the recommended installer.
	- graphify is an exception to the no-CLAUDE.md rule, and the only one (user, 2026-09-16). `graphify install --project --platform claude` is run as the tool intends. It writes two CLAUDE.md files, at the workspace root and under .claude/, registers two PreToolUse hooks, and installs the skill folder, .claude/skills/graphify/ with SKILL.md and its references/.
	- The CLAUDE.md files are deleted as soon as the install finishes (user, 2026-09-16). Their content already lives in the rule below, so keeping them buys nothing. Adapt's install and upgrade script runs graphify install, compares the fresh files against the source text kept with the draft rule, updates the rule if graphify changed its wording, and then deletes both files. An upgrade therefore recreates them only for the moment it takes to mine them.
	- Their content is mined into a gated rule that reaches a code specialist the moment it reads or modifies code in its own skill. The draft, with graphify's source text beside it for comparison at each upgrade, is spec/drafts/workspace-rule-tooling-graphify.md. The routing that makes that gate reach code outside the workspace is open (t63).
	- The two PreToolUse hooks are confined to the agents that use graphify. They move out of the workspace settings into the code specialist's agent definition, whose hooks field runs only while that agent is active, and they call the pinned environment's graphify by its absolute path. The manager never runs them.
	- A caveat from graphify's source: its hook-guard only nudges when an in-project graph exists, and it ignores reads of files outside the project. A specialist's skill copy sits outside the workspace, so the nudge may never fire there. The gated rule is what reliably carries the instruction; the hooks are kept as a second channel, not relied on.
	- graphify-out/ is always pointed with --out into the specialist's home, never left beside a host skill, because writing there would break the scope rule.
	- Its SKILL.md is about 41KB and its description claims "any question about a codebase", so it is preloaded only into specialists that work on code, and kept away from the manager.


Sessions and agents:
	THE MANAGER is a headless session, not a subagent. An Adapt command launches it inside the workspace, on the Opus 5 model, bare bones (a requirement). For now it is not launched with --bare, so it can use the subscription login instead of an API key billed directly. It is kept bare instead by the workspace sitting outside the host, and by its settings (open: t13). Its home folder holds its continuity files (see THE MANAGER below).
	The manager is the only instance that spawns or removes a subagent. By default a subagent may spawn its own subagents, up to three layers deep, so Adapt's settings set CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH to 1 to enforce this. It is also the only instance that creates the work items the specialists work on. It decides whether a skill is actually broken (REPAIR), needs extending (EXTEND), or whether a new skill is needed or is preferable to extending another (NEW).
	There are two kinds of subagent. Both are defined in .claude/agents/ with minimal starting directives, and both are preloaded with rules-system, vector-search and meta-tools:
	- Specialist, medium model (Sonnet). Each one is assigned one sibling skill and writes code for it. Specialists may work together on larger projects, such as building a brand new skill on request.
	- Specialist, lower model (Haiku). It carries out small file and folder operations for a medium specialist. Its context is wiped between every action, so every task given to it must be stateless. Tasks may be lumped together and done in batches. A medium specialist asks the manager for one when none exists, and the manager decides whether invoking it is worth it relative to the work. At least one should be kept available.
	This resembles Claude Code's agent teams. Agent teams do not run in a headless -p session, and teammates cannot spawn teammates, so Adapt builds the same shape from subagents plus files. (open: t15)
	Adapt can nest: an Adapt skill may contain another Adapt, forming chains of agents that build tools to help build tools. (open: t23)


Rules and protocols:
	Rules are the main guiding force. They decide much of the interplay between instances and guide their decisions, so they need careful design.
	- Adapt ships a starting set of rules. They can and probably will be modified, deleted and appended to.
	- Some rules are constants: never removed or modified. A rules-system config names them. (open: t16)
	- Protocols are rules assigned to every specialist when it is spawned. They give the specialist its workflow, and they can be tailored per specialist. (open: t18)
	- Adapt ships three of them, drafted before anything runs: the manager's round protocol, the specialist's work protocol, and the chore protocol for the low-model worker. They are what a fresh instance follows when it has no memory of anything, so they carry the sequence of the work, not advice (open: t52).
	- A protocol is a collection of rules, not one document. Rules are kept for their modularity and because they all live in one place. The collections sit in a protocols folder with two branches, one for the manager and one for the specialists; the chore worker's protocol sits with the specialists' until it proves it needs a branch of its own.
	- Each specialist gets its own copy of the specialist protocol on its first assignment, kept with its skill's rules, so it can be changed for that skill without disturbing any other specialist. The common branch is the template each copy starts from. A change to a copy still goes through the request scheme like any rule change.
	- A protocol is injected nearly at session start, before the agent has touched anything. A path gate cannot deliver it, because nothing has been touched yet, so the whole collection arrives through a startup mechanism (open: t18).
	- The work proceeds from both ends. The folder structures and the objects they hold (t53, t54, t55) are laid out while the protocols are drafted against the workflow already settled in this spec, and both are revisited often: the protocols are expected to be rebuilt many times before they work properly.
	- Every specialist has its own folder in rules/, named after the skill it is responsible for. All of that specialist's findings live there. The specialist curates its own findings and turns them into rules gated to particular code files or skill documents. (open: t24)
	- vector-search finds niche rules for a specialist to inject while it works on code. It also runs the audit tools that keep the rule set healthy: information independence (no redundancy), concise descriptions and proper scope.
	- vector-search also helps specialists navigate the code of the skill they work on, and the documentation they have collected on it that does not merit a finding.
	- Agent system prompts breadcrumb the knowledge each specialist needs, so it starts from a good point. (open: t17)
	- No agent edits a rule on its own account. A rule change is requested through the inbox and reviewed, like any other work: see Requests from inside Adapt.


Records and communication:
	Everything is kept as files and text, so it is all recorded and easy to look into, even at runtime.
	- Each specialist keeps its own history log, task window and questions file. They hold its working state and they are how it talks to the manager, to the host instance and to the user. What it puts there: what it did, its findings, its friction entries, and the complexity it runs into that needs judgement above its own.
	- A specialist writes a question into its questions file. A hook notifies the manager, which reads it and then answers it, passes it on to the host instance or the user, or turns it into work. Whatever channel carries the answer, including instance-to-instance messaging, the outcome and the answer land in the history log as text on disk, so the record outlives the session that produced it.
	- Anything that persists past the round is written by the manager. A specialist supplies the seed or the trigger for a rule; the manager creates and finalises it. That also settles who may write rules/INDEX.md while a round runs: only the manager.
	- vector-search keeps a separate index per kind of agent. A specialist has no reason to carry rules that do not apply to it.
	- The manager and every specialist has a notes folder of its own. Notes are freeform: an instance is encouraged to write there whenever it has something niche, half-formed, or with no other home, and to organise the folder with whatever subfolders and structure suit it.
	- A notes folder is never read whole at the start of a session. It is a library an instance builds over many sessions of working on one skill, or of managing, and it is reached by looking something up, not by loading it (open: t49).
	- Notes never replace the records. What happened belongs in the history log, what is next in the task window, and a fact that holds beyond one folder becomes a finding and then a rule. A note that turns out to be durable graduates; it does not sit in the notes folder as a second, competing home.
	- Use is counted. Every note carries how often it has been looked up and used, and a note with a high count is surfaced to the manager as a candidate finding. Frequency is the signal that something in the notes has become knowledge rather than a jotting.
	- Graduation removes the note. When the manager promotes one, the information moves into a rule, scoped to the parts of the skill where it will be needed, so it arrives at the moment it applies rather than waiting to be searched for. The note itself goes.
	- In time each specialist gets vector-search files of its own over its notes, so it can find the detail it would otherwise never locate, or assume was never written down.
	- The skill will be refined while it runs, so the records carry enough detail to refine from. The history logs and task windows are that detail; nothing separate is written for the user's benefit.
	- The manager's questions file doubles as a diagnostic while the design settles. When the manager does not know what to do, it writes the question there rather than guessing, and nobody has to answer at the time. The questions are read afterwards and answered structurally: a rule, a line in a protocol, a better briefing, or a tool. A question that keeps returning is a hole in the design, not a failing of the manager (open: t48).
	- The manager has its own history log, task file and questions file, created at initialization. An instance in the host project reads them in filtered slices by running a command against the Adapt skill. (open: t22)
	- Those three belong to the current round only. When a round starts, the previous round's copies move into that round's folder and the manager starts with empty ones (see Round). The manager's notes folder is not rotated; it persists across rounds.
	- The manager's task file lists all of its work, not only work items: spinning up agents, research, design considerations, and anything else it does. Each task ends with one line saying what was attempted and a single-word status, so nobody has to decipher the history log to learn how a task went.
	- The manager's task file IS the status surface. The user watches it in the viewer; a host instance reads it through the shim. Adapt builds no second status channel, because the manager has to keep that file anyway and status comes free with it.


Who Adapt answers to:
	Adapt exists for the host agent, not for the user directly. The manager reports to the instance that asked, and nothing waits on a person by default.
	The division is interface against implementation:
	- The host agent's concern stops at three things: its own intent, the surface the skills present, and how well that surface serves the intent. Below that line it is simply a user of the skills. If they work, they work; how they work is not its business.
	- The manager owns everything below that line: the internal design, and what each choice costs in effort, delay and tokens for the fixes and capabilities delivered back up.
	The manager's task file stays the status surface. The host agent reads it; the user watches it when they want to.
	One exception, while the skill is young: if a round stalls or crashes, the user is told directly. These are the days when that information is worth interrupting for, because the skill is still being built. The notice is a safeguard for this period, not part of the design's shape, and it can be retired once Adapt has proved itself (open: t47).


Scope, and the home folders:
	Adapt is insular. Its reach is deliberately local, and each agent has complete control over exactly one place: its own home folder.
	- The manager's home is adapt/manager_home/.
	- A specialist's home is adapt/specialists/<skill name>/<its home folder>. These are the folders the sections below call THE MANAGER and SPECIALISTS.
	- A specialist's home and its rules folder come into being on its first assignment, not at init. Inventory lists the sibling skills; it does not create a home for each. A skill nobody has asked about has no specialist and no folder.
	- Network access is kept to a minimum. The exception is the manager reading up on a topic when it needs to understand one well enough to write the right build request for its specialists.
	- Nothing outside a home folder is changed on an agent's own authority. This covers the host's hooks, rules, settings and source code, and Adapt's own internal structures as much as the host's.
	- An agent that believes one of those is wrong may say so, and should: it files a request. The request is adjudicated by a manager whose context is fresh, which means a new round or a newly spun-up manager instance, and it is implemented only on that manager's approval.


Submitting a request:
	The shim's SKILL.md carries an invocable command that walks the asking instance through the questions. It is an interview, not a blank form.
	- The questions differ by the nature of the request. A new capability or an extension is asked about one way, a repair another.
	- What the manager wants captured is the surface: the inputs, and what they deliver. A repair has the same shape: input x went in, z came out, y should have.
	- The middle is not asked for. How the thing is built is the manager's to decide, from research online or from what the specialist home folders already hold.
	- The form is dynamic. An answer is parsed as it is given and decides the follow-up question, so the asking instance is routed down the branch its own answers open.
	- One candidate for running that interview is a low-model instance working a decision tree. It may prove too much for that model; it is worth trying and measuring whether it routes the asking instance correctly (open: t51).
	- The aim is one pass: everything captured at submission, with no follow-up to the host instance, or as little as can be managed.


Requests from inside Adapt:
	Adapt may work on its own tooling, and on its own rules, but never by a shortcut. Everything inside uses the same inbox as an instance outside.
	- A specialist that wants a change to a skill or tool it uses drafts a request into the inbox in the course of its work and tells the manager it has done so. It does not make the change itself.
	- The manager reviews it like any other request. If it judges the request valuable it ratifies it, and it may extend the round in progress to include it as an item for the specialists.
	- The manager files its own requests the same way. It may never ratify a request in the round that wrote it. That takes a later round, whose manager started with fresh context.
	- The manager chooses the shape of the answer to a request. In order of how little it disturbs: repair what is broken; extend a skill that already does something close; wrap several skills behind one surface when composition delivers the capability best; or build a brand new skill when the functionality is entirely foreign, meaning nothing in the external-facing skills does it or anything like it. The last two are NEW requests.
	- A wrapper skill or a brand new one the manager itself proposes is filed in the inbox like any other request, and ratified by a later manager with fresh context, because this manager wrote it.
	- Every request is kept. Archiving is automatic, so what was asked survives the work item it became (open: t34).
	- Priority is the manager's job, weighed against the launch prompt and what it asked for. A tool earns its place by improving the delivery of the work item in hand on one of three measures: speed, usage and token efficiency, or ease of implementation, which covers both the complexity of the build and the chance of future breakage. When a tool is worth building first on those grounds, the manager may raise it above the external request; having done so, it runs another round for the external request.
	- Rules follow the same scheme. A specialist that wants a rule changed files a request and the manager reviews it. A rule change the manager itself wants is ratified only by a later manager round, with fresh context (open: t35).
	- Work on a tool happens in an isolated worktree or sandbox, so every agent, inside Adapt and outside it, keeps using the working version while maintenance is under way. The change merges only when the tests pass.


Retirement (open: t50):
	Adapt can retire what it maintains: a skill, a rule, or a meta tool. A set that only grows eventually costs more than it earns.
	- Retiring is a request like any other. It is reviewed and ratified by a manager with fresh context, and nothing goes on the authority of the agent that wants it gone.
	- The case is made from evidence, not opinion: a meta tool whose use count has stayed at nothing, a rule that never fires or that a newer rule covers, a skill whose surface nothing asks for any more. Use counts and firing logs are what make it.
	- A skill the host still uses is not retired, whatever Adapt thinks of it. The host's use is checked first.
	- A constant rule cannot be retired at all (open: t16).
	- Retirement archives rather than erases. The thing leaves the working set, and the record of what it was and why it went stays behind.


Tests and skill initialization:
	Testing is mostly automated, and it is set up before the work rather than after.
	- At init, Adapt takes inventory of the sibling skills in the host's skill folder.
	- The first time Adapt works on one of them, extending or repairing, that skill first goes through skill initialization: an automated test suite is built for it, before the change (open: t32).
	- The suites are meant to be robust: their job is to catch the change that quietly breaks something no instance thought to check.
	- They are maintained from then on. Work that adds behaviour adds its tests, and a repair adds the test that reproduces the fault.
	- Small meta tools carry less scrutiny. A meta tool under a size and line limit is narrow, highly specialised and internal-facing, and its documentation is whatever the agents that built it decide they need (open: t33).


Working on skills:
	Specialists change skills only on copies, probably git worktrees. The manager decides when a copy is merged back into the skill.
	A copy of a host skill is a git worktree made in the host repository by script. The isolation: worktree subagent field would copy the workspace repository instead, so Adapt does not use it for host skills.
	Copies live outside the manager's start folder and are reached through additionalDirectories. A copy under the start folder would let the session lazily load that copy's .claude/skills/.
	Rules still reach a copy, through a path map (user, 2026-09-16, option 1b of t63). The rules router matches paths relative to the workspace and ignores anything outside it, so a copy would otherwise get no rules at all.
	- The script that makes a copy writes one entry into .claude/copy-map.json in the workspace, pairing the copy's real folder with a short made-up path: C:/.../copies/my-skill-wi42/.claude/skills/my-skill/ becomes copies/my-skill/. The script that merges or discards the copy removes the entry, and rollback clears any entry a crash left behind.
	- Before matching, the router rewrites a real path under a mapped folder into its made-up path. Gates for a skill's code are written against the made-up path, copies/my-skill/**/*.py, so they carry no machine-specific paths and survive a move. The made-up path leaves out .claude/skills/ on purpose, because the router never gates anything under that prefix.
	- Agents are told the map exists, because their work can depend on it. The protocols of both the manager and the specialists say where the map is, what it does, and which made-up path belongs to the copy an agent works on. A specialist seeding a rule for its skill writes the gate against the made-up path, never the real one. An agent puzzled that a rule did or did not arrive checks the map first.
	When a specialist changes a sibling skill that Adapt also carries a copy of, the change is mirrored to Adapt's copy. A change to Adapt's copy is mirrored back the same way. (open: t20)


Where an improvement goes (open: t46):
	Adapt keeps a configuration, written when it is initialised in a project, with options per skill. Scripts maintain it: a skill discovered later is keyed into the configuration at the moment it is found, so the file never falls behind the folder.
	The options for a skill are:
	- Local, the default. The improvement changes the host project's copy and stops there. It favours the local approach: what one project needed does not become everyone's.
	- Global. The improvement is also merged into the skill's own repository, so other projects get it.
	- Later, a third: a retroactive reconciliation that takes what every Adapt instance has done to a skill and works it into a branch of that skill in its repository.
	Defaults exist for every option, and a skill may be set either way.
	Adapt's own runtime development follows the same shape, per host project by default. Rules created, changed or deleted, findings, and meta tools all stay in the workspace that produced them. This is a core part of the tool: Adapt changes itself out of the bespoke cases it meets, and those cases differ from project to project.
	When a change to Adapt's own workings looks like a net benefit in the general case, and not only here, it becomes a candidate to push and merge into the main branch of Adapt's repository, so other instances gain it too. It is a promotion on evidence, never an automatic sync.


Reading the inbox, and the answer that needs no engineering:
	- The manager reads every request in the inbox before it acts on any of them, and writes notes as it reads.
	- For a NEW or EXTEND request, its first question is whether an existing skill already does the thing and the host simply does not know. If one does, the manager answers the host with that skill's surface and a short piece of documentation that addresses the request, and closes the request. No work item is made.
	- Only when no existing surface answers the request does the manager weigh engineering.
	- To answer that first question, the manager keeps a high-level understanding of the surface of every sibling skill, and can look into a skill's internals through its graph. A skill with no specialist yet has no graph in a specialist home, so the manager can build and read one itself (open: t67).


The inbox and the three work folders (user, 2026-09-16):
	- INBOX holds raw requests, exactly as the guided request tool produced them, straight from the host. One file per request.
	- An automated log records everything that happens in the inbox folder: a request arriving, being read, amalgamated, answered from an existing skill, or turned into a work item.
	- NEW, EXTEND and REPAIR hold work folders, never raw requests. The manager creates a work folder from one or more inbox requests and places it in the folder for its kind: NEW for an entirely new skill, a wrapper skill included; EXTEND for an extension of an existing skill; REPAIR for a fix.
	- The original request is copied into its work folder, alongside what the manager writes there and what is generated there automatically, such as the group channel and the log.


The work item (user, 2026-09-16):
	A work item is a folder, and it is machine-facing: something a specialist can pick up and understand at once. Its contents are structured data where structure helps; JSON is the working suggestion, open to better.
	The folder exists to keep the information of one piece of work apart from the home folders. What belongs to this request, this repair, this extension stays in the work folder. What turns out to be useful beyond it is deposited into the manager's or a specialist's home, or promoted to a rule through the candidate process.
	What the folder holds:
	- The original copy of the request, or of each request amalgamated into it.
	- A coarse process spec written by the manager. For NEW or EXTEND work it says what the specialists must build, in outline. For a REPAIR it gives high-level guidance on how to probe for the fault and narrow down where in the code it lives, drawing on the skill's graph.
	- The acceptance tests, which are the main gate for completion. The manager designs the final test that must pass, and it is appended to the suite the specialist runs once it believes its work is done. Writing tests that cannot be trivially satisfied or gamed may be better done by a testing specialist with that knowledge (open: t56).
	- A history log that aggregates the history files of every specialist working on the item, pulled in by automated fixtures, so the item has one running log of events (open: t66).
	- A group channel: an append-only sequence of messages, like a history file, that every instance on the item can post to with a command, and read from in order, asking only for the entries it has not yet seen (open: t65).
	- Anything else that turns out to belong there.
	Tasks and links:
	- The manager tracks each work item as one task in its own task window, and that task points at the work folder.
	- A specialist that picks the item up processifies it as part of its protocol: it breaks the implementation into tasks of its own, in its own task window, linked back to the work folder. rules-system already links a sub-project to the task it serves (init --task, and the viewer opens a sub-project from its parent task); whether that link covers this shape is open (t68).
	End states:
	- A finished work folder is moved into a folder named for how it ended, such as Fulfilled, Aborted or Postponed. The states in between matter less than where the folder comes to rest.


Making sure a round delivered (open: t30):
	This is the hardest problem in the skill. Every agent starts with no memory of the last round, so nothing is caught by someone remembering. A specialist that believes it finished, a manager that believes the specialist, and a host instance told the work is done, is the failure this design has to make difficult. The answer is that a claim is never evidence, and that the checks are layered:
	1. The work item carries its acceptance criteria before any specialist touches it. The manager writes them from the inbox request, in the request's own words: what must be true, and how anyone would know. A work item without them is not assignable.
	2. A REPAIR starts with a failing test that reproduces the fault, written before the fix. An EXTEND or a NEW skill lands with tests for what it added. A skill that has a selftest runs it.
	3. The specialist reports evidence, not a summary: the diff, the commands it ran and their output, and each acceptance criterion paired with the evidence that satisfies it. An unmet criterion is reported as unmet, which is a normal outcome and never a failure of the specialist.
	4. A separate verifier subagent, with a fresh context, receives the work item, the acceptance criteria and the diff, and never the specialist's narrative. It re-runs the tests in a clean copy and tries to break the claim. Its job is to fail the work, not to agree with it.
	5. The manager merges on the verifier's pass and on the criteria being covered, never on either agent saying it is done. It sends the work back otherwise.
	6. After the merge, the host-side check runs the skill's own tests where it actually lives. A failure reverts the merge, and the round reopens rather than closing.
	7. There is no closing report (user, 2026-09-16). The manager's task for the work item ends with its one-line outcome and single-word status, and the host agent reads that from the manager's task file.
	Rollback is always available because the work is done on a copy: an unmerged branch is discarded, and a merged one is reverted.

Budget (open: t37):
	No caps for now. A round is not limited by a number of specialists, turns or minutes until there is a reason to limit it.
	A round that stops because the plan's included usage ran out is treated exactly as a crash: automated rollback, then the round is redone later from the known state. Running out of usage is a stop, never a half-finished merge.


Recovery from a crashed round (open: t38):
	A crashed round is redone from a known state, never salvaged. Rerunning from a state that is understood beats rescuing one that is not.
	- Rollback comes first, and in code wherever it can: the work happened on a copy, so the branch is discarded and its worktree removed, and a merge already made is reverted. An automated rollback is always preferred to an agent reasoning its way through wreckage.
	- What makes that possible is discoverability. Every agent logs its work to its history as it goes, and an active worktree or environment is marked active while it is in use, so a later session can find where changes were being made without guessing.
	- When the rollback cannot be automatic, the manager takes it. It establishes what was actually done in the folders that were active, decides what must be rolled back, and records both. This is manager work because it needs judgement rather than a script.
	- Once the state is known again, the round runs from the start.


The briefing (open: t31):
	Because no agent carries context between sessions, what each agent is given, and in what order, is the design rather than a detail. Each agent is started with, in this order: its own short system prompt; the protocol rules for its kind; the work item with its acceptance criteria; the pointers to where it works and what it may touch; and nothing else. Everything further is looked up: its rules folder, its history, its skill's documentation, and vector-search over the corpus. What is worth keeping is written back into those places before the agent ends, because the next agent will read them and not it.


Friction:
	A friction entry is a history entry that records something cumbersome in an instance's own workflow while it modifies, repairs or builds skills.
	- Instances weigh friction only as recurring or similar entries. A single entry is noise; a pattern may justify skill work that removes the friction for future work.
	- A hook tells an instance when it has accrued a configurable number of friction entries since the last notice, so no instance is notified after every prompt.
	- The manager looks into its own history and each specialist's history, filtered for friction. Diagnostic tools, and tools for boilerplate code that gets repeated often, are good candidates, whether the specialist or the manager spots them.
	- Specialists may file requests to improve their own workflow. The manager reviews them.
	- The main instance in the host project may use the same friction entries, with rules-system, to find which of its own skills are lacking or broken. It does not need them for this; it is a reuse of the skill at that level. (open: t19)


Initialization:
	Adapt goes through an install process the first time it is initialized. The init command has the manager spawn in and do the setup, together with many automated build scripts. It takes stock of the user's skill environment, creates the local data folders and other configuration it needs, loads its own skills, and creates the manager's history log and tasks file. It creates the workspace outside the host repository and writes the shim into the host's .claude/skills/adapt/. It also marks the workspace trusted, by writing hasTrustDialogAccepted for that path, because permissions.additionalDirectories is ignored until then and a headless session cannot answer the dialog. Everything that needs setting up happens during this first init. (open: t21)


Round (proposed; open: t12):
	A round is one start-to-finish cycle of work on one work item that the manager created from the inbox:
	1. The manager sorts the inbox and creates or updates the work item (see Amalgamation), filed under NEW, EXTEND or REPAIR.
	2. It assigns specialists to the work item, spawning any that are missing.
	3. The specialists work on a copy of the skill. They call on a lower-model specialist for batched, stateless chores.
	4. The manager reviews the result, then merges it or sends it back.
	5. The change is mirrored where needed and logged, and the inbox requests it covered are closed.
	One work item per round. The only work that may join it is an internal tool that directly improves the delivery of that item, judged on three things: speed, usage and token efficiency, and ease of implementation, meaning less complexity to build and less chance of future breakage and repair. A tool that improves none of them waits for its own round.
	A round can grow: the manager may ratify a request raised inside the round and add it as an item.
	A round can be reordered: when the manager promotes an internal tool above the external request, the external request waits for the next round.
	For now the user starts a round. Later the manager might start one itself. How much work a single round takes on is still open.
	Rounds are stateless with respect to each other (user, 2026-09-16). The instances of a round concern themselves only with that round's work, and a round never carries a follow-up of an earlier round's work. What does persist between rounds is the inbox, the work folders, the home folders and the rules; a later manager ratifying an earlier manager's request is reading the inbox, not inheriting a round. A host agent unhappy with a delivered result therefore files a new request (inferred from statelessness; not yet confirmed).
	Each round leaves a folder behind, generated automatically, in a rounds folder that belongs to the manager:
	- a file of references to the work items the round touched, by id or path;
	- the manager's history log, task file and questions file from that round, moved there when the next round starts, so the new round begins with empty ones.
	The round folders are diagnostic material: for the user refining the skill, and for the instances refining their own workflows. A round with no work items to do may, by the manager's protocol, read back through the round folders and propose improvements to the system from what it finds, as requests like any other.


Amalgamation (proposed; open: t9):
	Inbox requests that name the same skill and the same need merge into one work item. The same need means the same defect for REPAIR, or the same missing capability for EXTEND or NEW. vector-search suggests likely matches by meaning, and the manager confirms each merge. The work item keeps every source request's id, and it appends each submitter's added details instead of rewriting them. This is also how a piggyback request joins an existing one.

 RULES:
 Scope: the Documentation Dogma below applies only to the rules that govern THE MANAGER and the SPECIALISTS sub-agents, and to the documents they keep. It does not apply to the skills themselves or to the rest of the repo.

 Documentation Dogma:
	1) Information Independence
		There should be very little crossover of information between files.
	 Information files should strive for information independence similar to the idea of linear independence in linear algebra where vectors are independent of one another and cannot inform or construct the others due to the uniqueness they encode. The documents may have references to eachother but no more than that, so that information novelty is preserved and redundancy is killed.

	2) Condense, Compress, Refactor
		Always strive to express information in as dense a way as possible while still preserving meaning and comprehension.

	3) Context Is Tax Free
		Be holistic in expressing ideas. Details are important and you can never have too few details. This seems to run counter to number 2, but the desire is to encode enough information such that a brand new llm-instance may come across the contents of a file or folder where it is to live and work within and have enough information provided that it can use only what's there to completely resurrect past instances' context and start off as effectively as though it were the same instance.
